# 外部写入意图

负责登记对 GitHub 发起的外部写入意图，保证同一票据或父议题收尾门禁在同一时刻至多有一条在途活动意图，在调用前后记录执行状态并与最新源码事实核对确认，处理进程重启后的未决意图与主协调器的显式处置；不负责决定票据何时进入发布、合并或关单阶段。

## 依据

通过 `gh` CLI 或 HTTP 接口向 GitHub 发起创建拉取请求、合并拉取请求、修改议题状态等写操作时，超时、断连或多步命令中途退出均不证明远端未生效（来源：GitHub CLI 与 HTTP 接口行为，证据见附录 `evidence/github-write-uncertainty.md`）。所以每次写入前必须先经 ``Effect`BeginExecute`` 持久化为 ``<Executing>``，调用后仅凭最新源码读取经 ``Effect`Confirm`` 确认；未获确认或重启遗留的执行中意图经 ``Effect`Fail`` 或 ``Effect`RecoverExecuting`` 转入 ``<Uncertain>``，交主协调器经 ``Effect`Dispose`` 显式处置。

## 为什么

外部写入意图的状态流转（就绪、执行中、已确认、失败、结果未知、已取消）只用到父模块的 ``Ticket`TicketId``，父模块只需在意图经源码确认或失败后推进或升级票据，不需要知道每次外部调用如何持久记录与对账，所以单独成为子模块。

不把外部写入意图内嵌为 ``Ticket`TicketStage`` 的字段：除发布拉取请求、合并拉取请求和关闭议题外，主协调器在裁定升级票据时还会发起创建子议题（``<CreateIssue>``）、挂接子议题（``<AttachChild>``）、替换议题正文（``<ReplaceBody>``）与重跑检查（``<RerunChecks>``）等写入，一张票据在生命周期中会产生多条历史意图记录；独立成表并在 ``Effect`Effects`` 上约束同一主体至多一条在途活动意图，才能统一管理全部外部写入的幂等对账与崩溃恢复。

## 语义

`Effect` 与 `Ticket` 运行在同一协调器进程内，意图表随议程状态在同一原子文件写入中持久化。任何处于 ``<Executing>`` 的意图在进程重启接管时只调用一次 ``Effect`RecoverExecuting`` 转为 ``<Uncertain>``，协调器绝不在无人裁定时自动重发该外部请求。
