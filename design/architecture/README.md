# 议程与票据协调

负责维护议程中的票据依赖图、源码契约指纹与门禁印记，按经源码确认的事实推进票据与父议题收尾门禁的阶段流转，并向主协调器与席位提供派发、提交、裁决、升级与裁定连接；不负责外部写入意图的持久对账、席位会话与工作树的宿主管理、主协调器唤醒去重，以及本地链接启动器。

## 依据

GitHub 上的议题正文、拉取请求头提交、合并状态、必需检查与目标分支随时可能由外部独立变更（来源：GitHub 平台行为，证据见附录 `evidence/github-source-drift.md`）。所以门禁裁决绑定由议题契约、拉取请求与裁定共同构成的 ``Ticket`Stamp`` 指纹；审查阶段拉取请求推进时重开门禁，合并阶段指纹漂移或议题契约变更时票据经 ``Ticket`Escalate`` 转入 ``<Escalated>`` 交主协调器裁定。

拉取请求合并到目标分支后，目标分支提交历史与议题关闭状态仍可能偏离交付契约（来源：系统级需求）。所以合并确认后票据经 ``Ticket`ConfirmMerge`` 进入 ``<Verifying>`` 由合并后门禁核验目标分支包含关系，全部子票据到达 ``<Done>`` 后父议题再经 ``Ticket`ClosureGate`` 收尾门禁核验。

同一议程中无依赖关系的票据可并行推进，有依赖关系的票据必须等待前置票据完成交付后才能启动或合并（来源：系统级需求）。所以 ``Ticket`Agenda`` 维护无自环依赖图，导出纯函数 ``Ticket`DependenciesDone`` 与 ``Ticket`Launchable`` 判定票据何时允许放上桌面。

外部写入（发布拉取请求、合并拉取请求、关闭议题）在网络超时或进程中断时仍可能已在远端生效（来源：GitHub CLI 与 HTTP 接口行为，证据见附录 `evidence/github-write-uncertainty.md`）。所以票据提交与门禁通过后先进入 ``<Publishing>`` 与 ``<Merging>`` 等待源码确认，持久写入意图与崩溃对账拆入子模块 `Effect`。

代码编写席位需要沿用同一工作树与会话历史做返工，而审查、验收、合并后核验与父议题收尾门禁必须在干净检出上独立评判且同一修订号只派发一次（来源：系统级需求）。所以票据每次门禁失效或升级都递增 ``Ticket`Revision`` 并清空旧门禁结论，席位宿主生命周期拆入子模块 `Seat`。

任何网页都能通过图片或预取向本地回环端口发起请求，且 GitHub 在跨协议跳转时剥离来源头，同时终端守护进程在无窗口时仍保持后台运行（来源：浏览器安全策略与 Tern 行为，证据见附录 `evidence/browser-navigation-and-tern.md`）。所以本地启动器拆入子模块 `Launcher`，仅响应带用户激活导航头的点击并确保终端窗口可见。

## 为什么

票据图、票据阶段、门禁记录与父议题收尾门禁放在同一个根模块 `Ticket`，因为它们共享“依赖边不出议程票据集且已完成的议程中全部票据与父议题收尾门禁均已完成”这条议程不变量（``Ticket`Agenda``）。不把门禁结论与票据阶段拆成两个互相同步的表：门禁是否有效直接取决于票据当前修订号与 ``Ticket`Stamp``，拆开后需要额外对账防止过期门禁触发合并。

不让席位直接向 GitHub 创建或合并拉取请求：席位只能经 ``Ticket`Submit``、``Ticket`Verdict`` 与 ``Ticket`Escalate`` 交回结论，由协调器在核验源码指纹与前置依赖满足后统一驱动 `Effect`，避免并发席位越过门禁修改远端状态。

## 语义

协调器进程由 `--roundtable <owner>/<repo>#<number>` 启动参数唯一标识，在其生命周期内绑定唯一的原生主会话；未传该参数时扩展不注册活动工具、定时器或持久状态。

协调器每隔 ``Ticket`RecomputeSeconds`` 秒主动读取一次 GitHub 事实并执行对账；每次状态变更在返回前以格式版本 ``Ticket`StateFormat`` 原子写入本地状态目录并同步目录项（实现参考见附录 `reference/storage-and-worktrees.md`）。

`Ticket`、`Effect`、`Seat` 与 `Attention` 运行在同一协调器进程内；进程崩溃重启后，新进程必须经操作员确认原协调器进程已结束后接管活动议程。
