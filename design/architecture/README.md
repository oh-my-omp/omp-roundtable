# 议程与票据协调

负责维护议程中的票据依赖有向无环图、阶段门禁载荷与源码指纹，按经 GitHub 源码确认的观测事实推进子票据与父议题收尾门禁的阶段流转，并向主协调器与席位提供召集、派发、提交、裁决、对账、升级与裁定连接；不负责外部写入意图的持久对账、席位会话与工作树的宿主管理、主协调器唤醒去重，以及本地链接启动器。

## 依据

GitHub 上的议题正文、拉取请求头提交、合并状态、必需检查与目标分支随时可能由外部独立变更（来源：GitHub 平台行为，证据见附录 `evidence/github-source-drift.md`）。所以审查与验收门禁共同绑定 ``Ticket`ReviewGates`` 中的 ``Ticket`Stamp`` 指纹，对账操作 ``Ticket`ReconcileTicket`` 在审查期拉取请求指纹推进时重开双门禁，在契约或合并期指纹漂移时将票据转入 ``<Escalated>`` 交主协调器裁定。

拉取请求合并到目标分支后，目标分支可能因并发提交或回滚而不包含该合并提交，且远端议题可能尚未关闭或被重新打开（来源：GitHub 分支与议题状态行为，证据见附录 `evidence/github-source-drift.md`）。所以合并确认后票据经 ``Ticket`ConfirmMerge`` 进入携带 ``Ticket`VerifyGate`` 的合并后核验阶段，必须待合并后门禁通过且议题关闭经源码确认后才经 ``Ticket`ConfirmDone`` 进入 ``Ticket`DoneStage``。

父议题的交付契约跨越全部子议题的集成结果，单个子票据的门禁无法独立证明父议题整体完成（来源：系统级需求）。所以当议程包含父议题时，``Ticket`Agenda`` 维护与子票据身份不重叠的 ``Ticket`ClosureGate``，仅在全部子票据到达 ``Ticket`DoneStage`` 后才开放 ``<Closure>`` 席位核验并在失败时支持经 ``Ticket`ResolveClosure`` 重开。

同一议程中无依赖关系的票据可并行推进，有依赖关系的票据必须等待前置票据完成交付后才能启动或合并（来源：系统级需求）。所以 ``Ticket`Agenda`` 维护无自环依赖图，导出纯函数 ``Ticket`DependenciesDone``、``Ticket`Launchable`` 与 ``Ticket`ReadyToMerge`` 判定票据何时允许放上桌面或进入合并。

外部写入（发布拉取请求、合并拉取请求、关闭议题）在网络超时或进程中断时仍可能已在远端生效（来源：GitHub CLI 与 HTTP 接口行为，证据见附录 `evidence/github-write-uncertainty.md`）。所以票据提交、双门禁通过或裁定无需代码后分别进入 ``<Publishing>``、``<Merging>`` 与 ``<ClosingNoCode>`` 等待源码确认，持久写入意图与崩溃对账拆入子模块 `Effect`。

代码编写席位需要沿用同一工作树与会话历史做返工，而审查、验收、合并后核验与父议题收尾门禁必须在干净检出上独立评判且同一修订号只派发一次（来源：系统级需求）。所以票据每次门禁失效或升级都递增 ``Ticket`Revision`` 并替换阶段载荷，席位宿主生命周期拆入子模块 `Seat`。

## 为什么

票据图、票据阶段载荷与父议题收尾门禁放在同一个根模块 `Ticket`，因为它们共享“依赖边不出议程票据集、未启动票据不进入执行后阶段、父议题收尾门禁身份与子票据互斥、议程完成时全部票据与收尾门禁均已完成”这条议程不变量（``Ticket`Agenda`` 与 ``Ticket`TicketEntry``）。不把门禁结论存成与阶段平行的可空字段：将 ``Ticket`ReviewGates``、``Ticket`VerifyGate`` 与 ``Ticket`DoneStage`` 作为 ``Ticket`TicketStage`` 的和类型分支，由构造保证审查与验收共享同一指纹且非门禁阶段不残留过期门禁记录。

将合并前门禁拆为独立的 ``<Review>`` 与 ``<Accept>`` 两个角色，并单列合并后的 ``<PostMerge>``：代码审查聚焦变更实现质量，验收聚焦议题需求兑现，二者在独立会话中并行评判同一拉取请求头提交；合并后核验则在目标分支合并提交上确认集成结果，职责与检出基准不同，不能合并为单一门禁。

不让席位直接向 GitHub 创建或合并拉取请求：席位只能经 ``Ticket`Submit``、``Ticket`Verdict`` 与 ``Ticket`Escalate`` 交回结论，由协调器在核验源码指纹与前置依赖满足后统一驱动 `Effect`，避免并发席位越过门禁修改远端状态。

进程崩溃后要求操作员确认原协调器进程已结束才允许接管，而不采用文件锁自动抢占：协调器在途派发的外部 CLI 子进程无法被新进程远程撤销，盲目抢占会导致新旧两个协调器并发写同一议程与远端仓库。

由于设计目录采用单根模块布局，根模块 `Ticket` 代表圆桌协调核心，`Effect`、`Seat`、`Attention` 与跨进程启动器 `Launcher` 作为仅单向引用 `Ticket` 基础类型的子模块挂载在根目录下。

## 语义

协调器进程由 `--roundtable <owner>/<repo>#<number>` 启动参数唯一标识，在其生命周期内绑定唯一的原生主会话；未传该参数时扩展不注册活动工具、定时器或持久状态。

协调器按固定周期主动读取 GitHub 事实并执行 ``Ticket`ReconcileTicket`` 对账；每次状态变更在返回前原子写入本地状态目录并同步目录项（轮询间隔、格式版本与原子落盘做法见附录 `reference/storage-and-worktrees.md`）。

`Ticket`、`Effect`、`Seat` 与 `Attention` 运行在同一协调器进程内；`Launcher` 运行在独立的本地无状态驻留进程中，与协调器不同存续期。`Seat` 派发的子席位会话作为协调器进程内的无界面原生子会话运行在独立工作树中，仅持有绑定单张票据的受限工具，不加入跨会话广播，也不直接执行 GitHub 写操作。
