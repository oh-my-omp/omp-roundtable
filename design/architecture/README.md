# 议程与票据协调

负责维护议程中的票据依赖图、源码指纹与门禁核验集合，保证票据仅在前置依赖完成且当前源码指纹下的必需门禁全部通过后完成；不负责具体业务阶段的编排、外部写入意图的持久对账、席位会话与工作树的宿主管理、主协调器唤醒去重，以及本地链接启动器。

## 依据

远端仓库中的议题正文、分支提交与检查状态随时可能由外部独立修改（来源：GitHub 平台行为，证据见附录 `evidence/github-source-drift.md`）。所以门禁通过记录绑定在票据当前的 ``Ticket`Stamp`` 上；源码指纹变更（``Ticket`RefreshStamp``）或升级（``Ticket`Escalate``）时递增 ``Ticket`Revision`` 并清空已通过门禁集合。

同一议程中无依赖关系的票据可并行推进，有依赖关系的票据必须等待前置票据完成后才能启动或完成（来源：系统级需求）。所以 ``Ticket`Agenda`` 维护无自环依赖图，由纯函数 ``Ticket`DependenciesDone`` 与 ``Ticket`Launchable`` 判定票据何时允许启动与完成。

外部写入在网络超时或进程中断时仍可能已在远端生效（来源：GitHub CLI 与 HTTP 接口行为，证据见附录 `evidence/github-write-uncertainty.md`）。所以持久写入意图与崩溃对账拆入子模块 `Effect`。

编写者席位需要沿用同一工作树与会话历史做返工，而核验门禁席位必须在干净检出上独立评判且同一修订号只派发一次（来源：系统级需求）。所以席位宿主生命周期拆入子模块 `Seat`。

任何网页都能向本地回环端口发起子资源请求，且终端守护进程在无窗口时仍保持后台运行（来源：浏览器安全策略与 Tern 行为，证据见附录 `evidence/browser-navigation-and-tern.md`）。所以本地点击授权与终端窗口探活拆入子模块 `Launcher`。

## 为什么

票据依赖图、源码指纹与门禁集合放在同一个根模块 `Ticket`，因为它们共同守住“依赖边不出议程票据集、未启动票据不得记录门禁通过或完成、已完成票据必已通过当前指纹下的全部必需门禁”这条不变量（``Ticket`Agenda`` 与 ``Ticket`TicketRecord``）。不在架构层枚举具体的业务阶段名称或固定门禁名单：将门禁抽象为 ``Ticket`Gate`` 集合，无需代码的裁定即对应空门禁集合，使具体业务流程变化时核心连接与不变量保持不变。

进程崩溃后要求操作员确认原协调器进程已结束才允许接管，而不采用文件锁自动抢占：协调器在途派发的外部 CLI 子进程无法被新进程远程撤销，自动抢占会导致双写。

## 语义

协调器进程由 `--roundtable <owner>/<repo>#<number>` 启动参数唯一标识，在其生命周期内绑定唯一的原生主会话。每次状态变更在返回前原子写入本地状态目录并同步目录项（实现参考见附录 `reference/storage-and-worktrees.md`）。

`Ticket`、`Effect`、`Seat` 与 `Attention` 运行在同一协调器进程内；`Launcher` 运行在独立的本地无状态驻留进程中，与协调器不同存续期。
